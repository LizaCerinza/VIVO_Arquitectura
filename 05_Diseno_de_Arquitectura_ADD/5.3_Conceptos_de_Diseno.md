# 5.3 Conceptos de diseño utilizados

En ADD, los **conceptos de diseño** son las soluciones probadas que se eligen en cada iteración:

- Arquitecturas de referencia o estilos.
- Patrones.
- Tácticas.
- Componentes desarrollados externamente.

## Estilo de arquitectura: alternativas evaluadas

| Alternativa | Ventajas | Limitaciones | Decisión |
|---|---|---|---|
| Aplicación síncrona única | La más simple de construir. | La recepción queda atada al RNDC: si el RNDC cae, VIVO deja de recibir (incumple D-01). | Descartada |
| **Monolito modular + proceso de fondo + cola durable** | Límites claros entre módulos, una sola base de código, separa recepción y trámite y es operable por un equipo pequeño (RT-05). | Requiere operar una cola y dos procesos, con consistencia eventual. | **Seleccionada** |
| Microservicios | Despliegue y escalado independientes por servicio. | Más infraestructura, red y fallas distribuidas. No se justifica con unas 1.500 solicitudes al día ni con un solo equipo. | Descartada por ahora; se revisa si crece el volumen o el número de equipos |

## Conceptos por categoría

| Concepto | Tipo | Driver | Para qué lo usamos |
|---|---|---|---|
| Monolito modular | Estilo | D-04, RT-05 | Módulos con responsabilidades claras (recepción, identidad, solicitudes, auditoría) en una sola aplicación desplegable. |
| Procesamiento asíncrono con cola durable (*Queue-Based Load Leveling*) | Patrón | D-01 | Separar la recepción del trámite y absorber las ráfagas y las caídas del RNDC. |
| Puertos y adaptadores (hexagonal) | Patrón | D-04 | La lógica de negocio no conoce los protocolos del RNDC ni de WhatsApp: solo habla con interfaces (puertos). |
| Capa anticorrupción (DDD) | Patrón | D-04 | Traducir el modelo y los códigos de respuesta del RNDC al modelo interno de VIVO. |
| Circuit Breaker, timeouts, reintento con espera creciente, throttling | Patrón y tácticas | D-01, RT-04 | Proteger a VIVO y al RNDC durante fallas. |
| Transactional Outbox | Patrón | D-02 | Guardar la solicitud y su tarea en una sola transacción, sin pérdida entre guardar y publicar. |
| Receptor / consumidor idempotente y llave de idempotencia | Patrón y táctica | D-02 | Evitar solicitudes y manifiestos duplicados por mensajes o reintentos repetidos. |
| Máquina de estados con verificación de transiciones | Táctica | D-02 | Solo transiciones válidas; «Emitida» únicamente con número oficial. |
| Scheduler Agent Supervisor (conciliador) | Patrón | D-02 | Resolver estados intermedios o inciertos consultando antes de reintentar. |
| Bitácora inmutable (*append-only*) | Táctica | D-05 | Evidencia de cada estado e intento. |
| Security Gateway + Intercepting Validator | Patrón | D-03 | Único punto de entrada que valida la firma del webhook y la entrada. |
| Autorización por objeto y separación por empresa | Táctica | D-03 | Verificar en cada operación que la solicitud pertenezca a la empresa del usuario. |
| Auditoría, no repudio y cifrado | Táctica | D-03, D-05 | Registro inalterable de accesos y protección de datos personales (Ley 1581). |
| Monitor, ping/eco y alertas | Táctica | D-01, PA-02 | Detectar fallas del RNDC, vigilar pendientes y avisar al administrador. |
| Repuesto redundante activo (2 instancias de la API) | Patrón | D-01 | Que una falla de una instancia de VIVO no detenga la recepción. |

## Componentes y tecnologías externas

Definimos **familias** de tecnología y no productos concretos. El producto se elige al implementar.

| Elemento | Familia de tecnología | Ejemplos posibles |
|---|---|---|
| Canal de mensajería | WhatsApp Business Platform (Cloud API) | — (restricción RT-02) |
| API Gateway | Gateway de API gestionado o proxy inverso | AWS API Gateway, Kong, Nginx |
| Base de datos | Relacional transaccional (ACID) | PostgreSQL |
| Cola durable | Broker de mensajes con persistencia y cola de mensajes fallidos (DLQ) | RabbitMQ, Amazon SQS |
| Monitor y alertas | Plataforma de observabilidad | CloudWatch, Prometheus + Grafana |
| Secretos | Gestor de secretos | AWS Secrets Manager, Vault |
