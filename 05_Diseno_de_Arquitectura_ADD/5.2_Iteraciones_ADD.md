# 5.2 Iteraciones ADD

Aplicamos ADD 3.0 (Cervantes & Kazman, *Designing Software Architectures*, 2016). Cada iteración sigue los mismos pasos:

1. Revisar las entradas.
2. Fijar el objetivo de la iteración y elegir sus drivers.
3. Elegir los elementos a refinar.
4. Elegir los conceptos de diseño.
5. Instanciar elementos y asignar responsabilidades.
6. Bosquejar vistas y registrar decisiones.
7. Analizar si se cumple el objetivo.

## Resumen

| Iteración | Objetivo | Drivers | Elemento refinado | Resultado |
|---|---|---|---|---|
| 1 | Estructura general del sistema | D-01, RT-05, CU-01, CU-02 | VIVO completo | Monolito modular + procesador de fondo + cola durable + base de datos |
| 2 | Integración con proveedores externos | D-04, D-01 | Procesador RNDC y API | Adaptadores aislados (puertos y adaptadores) con Circuit Breaker |
| 3 | Integridad y trazabilidad del estado | D-02, D-05 | API, base de datos, procesador | Outbox, idempotencia, máquina de estados, conciliador y bitácora |
| 4 | Seguridad entre empresas | D-03 | Entrada, API, base de datos | API Gateway (Security Gateway), autorización por operación, separación por empresa |
| 5 | Preocupaciones transversales | PA-01 a PA-04, D-01 | Todo el sistema | Monitor y alertas, redundancia de la API, simuladores para pruebas |

---

## Iteración 1 · Estructura general

| Paso | Contenido |
|---|---|
| **Objetivo** | Definir la estructura inicial que permita recibir solicitudes sin depender del RNDC. |
| **Drivers** | D-01, RT-05 (equipo pequeño), CU-01, CU-02. |
| **Elemento a refinar** | El sistema VIVO completo. |
| **Conceptos elegidos** | Estilo **monolito modular** con un **proceso de fondo** (*worker*) y una **cola durable** (procesamiento asíncrono). Alternativas descartadas: aplicación síncrona única y microservicios (ver [5.3](5.3_Conceptos_de_Diseno.md)). |
| **Elementos instanciados** | API de Recepción y Gestión (recibe, valida y guarda), Procesador RNDC (tramita en segundo plano), Cola durable (tareas pendientes), Base de datos transaccional, Consola de Administración. |
| **Análisis** | EC-01: la API confirma la recepción después de guardar, sin llamar al RNDC, así que una caída del RNDC no detiene la recepción. ✔ |

## Iteración 2 · Integración con proveedores externos

| Paso | Contenido |
|---|---|
| **Objetivo** | Aislar al RNDC y a WhatsApp para que sus fallas o cambios no se propaguen. |
| **Drivers** | D-04, D-01. |
| **Elemento a refinar** | Procesador RNDC (salida al RNDC y a WhatsApp) y API (entrada de WhatsApp). |
| **Conceptos elegidos** | **Puertos y adaptadores** (arquitectura hexagonal) y **capa anticorrupción** (DDD, Evans) para traducir el contrato del RNDC. **Circuit Breaker**, **timeouts**, **reintento con espera creciente** y **throttling** (Punto 4, EC-01). |
| **Elementos instanciados** | Adaptador RNDC con control de llamadas, Adaptador de WhatsApp de entrada (webhook) y de salida (notificaciones). |
| **Análisis** | Un cambio en el contrato del RNDC solo toca su adaptador. El circuito abierto evita saturar al RNDC (RT-04). ✔ |

## Iteración 3 · Integridad y trazabilidad

| Paso | Contenido |
|---|---|
| **Objetivo** | Garantizar que ninguna solicitud se pierda o se duplique y que todo cambio de estado quede registrado. |
| **Drivers** | D-02, D-05. |
| **Elemento a refinar** | API, base de datos y Procesador RNDC. |
| **Conceptos elegidos** | **Transactional Outbox**, **receptor/consumidor idempotente**, **llave de idempotencia**, **máquina de estados** con verificación de transiciones, **Scheduler Agent Supervisor** (conciliador) y **bitácora inmutable** (Punto 4, EC-02). |
| **Elementos instanciados** | Tabla outbox y su *relay* (en la API), conciliador (en el Procesador), bitácora de estados e intentos (en la base de datos). |
| **Análisis** | EC-02: ante una respuesta incierta se consulta antes de reintentar. Ningún estado pasa a «Emitida» sin número oficial. ✔ Queda por validar si el RNDC permite consultar el estado. |

## Iteración 4 · Seguridad entre empresas

| Paso | Contenido |
|---|---|
| **Objetivo** | Impedir el acceso cruzado entre empresas y dejar evidencia de cada intento. |
| **Drivers** | D-03 (y D-05 para la auditoría). |
| **Elemento a refinar** | Punto de entrada, API y base de datos. |
| **Conceptos elegidos** | **Security Gateway** con **Intercepting Validator** (firma del webhook), **autorización por empresa en cada operación**, **separación de entidades** (filtro obligatorio por empresa), **cifrado**, **auditoría** y **no repudio** (Punto 4, EC-03). |
| **Elementos instanciados** | Contenedor API Gateway. Módulo de identidad y autorización y módulo de auditoría dentro de la API. |
| **Análisis** | EC-03: el acceso a una solicitud de otra empresa se rechaza en la operación misma y queda auditado. ✔ |

## Iteración 5 · Preocupaciones transversales

| Paso | Contenido |
|---|---|
| **Objetivo** | Hacer el sistema operable, observable y fácil de probar. |
| **Drivers** | PA-01 a PA-04, D-01 (meta de recepción ≥ 99,5 %). |
| **Elemento a refinar** | Todo el sistema. |
| **Conceptos elegidos** | **Monitoreo de condiciones** y **ping/eco** (sonda del RNDC), **repuesto redundante** activo para la API, gestor de secretos y simuladores del RNDC y de WhatsApp para pruebas. |
| **Elementos instanciados** | Contenedor Monitor y Alertas. Dos instancias de la API detrás del gateway. |
| **Análisis** | Las alertas y la sonda cubren las medidas de EC-01 (alerta ≤ 5 min, reanudar ≤ 15 min). La redundancia apoya la meta de recepción ≥ 99,5 %. ✔ |

> Las decisiones más importantes de estas iteraciones se registran como ADR en el [Punto 6](../06_Decisiones_de_Arquitectura_ADR/06_Decisiones_de_Arquitectura_ADR.md).
